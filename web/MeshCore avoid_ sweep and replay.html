Results for the protocol as published were produced from commit 679e72e, and results for the mid-edge stop from commit 9dbd87e (see Data availability). ## Abstract Robots working the same field need to keep apart when the only link is a low-bandwidth radio that drops frames. We evaluate a decentralised node-claim protocol, implemented in the open-source `sowbot-avoid` package, for row-crop robots on a MeshCore LoRa mesh. Each robot sends one 8-byte frame on reaching each node, naming the node it stands on and the next two nodes of its route, and moves only if no peer's hold or claim blocks its next edge. There are no resends and no central coordinator. We simulate it on a virtual clock with a shared channel that loses overlapping frames and adds random loss and delay. On a generated 336-node map (16 rows × 60 m) with 2–4 robots, frame loss of 0, 10 and 20% and 10 seeds per case, 73 of 90 runs finished and 3 had two moving robots come within the 1 m clearance, all with 4 robots and at least one lost frame. A traced case shows the cause: two robots' frames were lost, so each drove toward the same node unseen, and the arrival frame that would have shown the conflict is sent only 2 s after arrival. We then let a robot stop part-way along an edge when a frame shows a conflict. It raised the closest approach in that run from 0.00 m to 0.73 m, still under the clearance, and did not reduce the number of close approaches (3 of 90) or the number of runs that finished (72 of 90). With routes 20 legs long (90 runs per configuration), 18 runs had a close approach without the stop and 14 with it, and 23 and 14 runs finished. On those runs close approaches also occurred with 3 robots and became more frequent as loss rose. The protocol as implemented does not keep clear under frame loss. The code, map generator and sweep tool are public. It has never run on hardware. **Keywords:** agricultural robotics, multi-robot systems, collision avoidance, LoRa, decentralised coordination, communication loss ## 1. Introduction Small robots working row crops are often run in groups, and a group needs a way to stay apart. A central planner needs a reliable link to every robot. Fields often lack cellular coverage, and long-range radios such as LoRa carry a few bytes per frame and lose some of them. Shamshiri et al. (2024) built a LoRa link between an operator and an orchard robot and measured an average packet loss of 12% at about 2300 m. That work concerns the operator-to-robot link, not robots sharing a field with each other. Lautenschlaeger and Sommer (2022) studied plain LoRa as a mesh between machines working one field in parallel, with field experiments and simulation, but for sharing work already done (section control), not for collision avoidance. We evaluate a protocol in which each robot announces where it is and where it intends to go next, and every robot decides for itself whether to move. It was proposed for the Sowbot open-hardware agricultural robot (Sowbot issue 202) and implemented in `sowbot-avoid`, which runs over MeshCore. The package states that it is simulated only, has never run on hardware, and is not a safety function: onboard obstacle detection stays in charge. The question is how the protocol behaves when frames are lost. The contributions are: - a description of the protocol as implemented, with its exact priority and timing rules; - sweeps on a generated 336-node map of 90 runs with 1 leg per route, 40 with 6 legs and 180 with 20 legs, showing where it keeps clear and where it does not; - a traced example of how lost frames lead to a close approach, and a test of one fix, stopping a robot part-way along an edge; and - the public code and sweep tool, so that every run can be repeated and replayed. ## 2. Related work **LoRa in agriculture.** Shamshiri et al. (2024) measured LoRa packet loss between an operator and a robot in berry orchards. Lautenschlaeger and Sommer (2022) investigated plain LoRa, as opposed to LoRaWAN, for connected machines working one field, and found it a promising basis, including without line of sight. Neither addresses collision avoidance between robots. **Communication loss in multi-robot teams.** Zhivkov et al. (2017) injected random packet loss from 0 to 75% into physical and simulated multi-robot teams and found that performance fell non-linearly as loss rose. Zhivkov and Sklar (2020) modelled signal strength instead of using a fixed loss rate. Abu-Aisheh et al. (2021) show that a swarm exploration algorithm must take packet loss into account. We use random loss as the earlier studies do, with the same limitation. **Reservations and deadlock.** Conflict-free routing of automated guided vehicles is a classic problem. Kim and Tanchoco (1991) reserve time windows on nodes, and Sarker and Gurav (2005) design a path layout and routing algorithm that guarantee conflict-free routes. Pratissoli et al. (2024) prevent deadlock on a roadmap with a hierarchical coordinator, and Henkel and Toussaint (2020) pair roadmap graphs with decentralised planners and online collision avoidance. These approaches assume a scheduler or reliable messaging. The protocol here has neither: claims are broadcast, unconfirmed, and decided locally. ## 3. Protocol The description follows the package documentation and `agent.py` at the commits above. ### 3.1 Frames The map is a graph of nodes joined by two-way edges. Every robot carries the same map and a fixed route of nodes. On reaching a node, and once at start-up, a robot sends one frame: its ID, an 8-bit sequence number and up to three nodes. The first node is where it stands (its *hold*). The next two are the edges it plans to drive (its *claims*). A frame is at most 8 bytes and 21 bytes on air as a MeshCore group data packet. Receivers keep only the latest frame per peer. There are no confirmations and no resends. ### 3.2 Rules Two stretches of path conflict if they come closer than a clearance (1 m here). Before driving an edge, a robot checks every peer. It must wait if: 1. the peer's hold conflicts with the edge; or 2. the peer's claim conflicts with the edge, and either the peer has a lower ID, or the peer's last frame was received 1.5 s ago or longer (it is treated as committed). After announcing, a robot waits 1.5 s for rival claims. After a move it waits 2 s before sending the arrival frame, so peers keep seeing its old node as held while its tail clears. Before sending it waits while any frame was heard in the last 0.1 s, backing off 0.12 to 0.48 s for at most 2 s. Start-up has a random delay of 0 to 1 s. ### 3.3 Side-stepping A robot blocked for 3 s only by higher-ID peers side-steps to the nearest free waiting spot in a crop row, announces its position without claims, waits until its route onward is clear, and continues. It may do this at most 10 times. A robot blocked by a lower-ID peer never side-steps. ### 3.4 Known limitations The package states three. Stored positions never expire, so a robot that dies while claiming a stretch blocks it for good. A finished robot never releases its last position, so it blocks that node and everything within the clearance for the rest of the run. Head-on meetings on tight maps can use up all 10 side-steps. A fourth follows from reading `agent.py` and the driver interface: a robot checks for blockers before it drives an edge and not during it, because the driver call returns only on arrival. ### 3.5 Mid-edge stop (added for this study) We added an option, `react`, that addresses the fourth limitation. The agent runs the driver call as a task. While it runs, each frame that arrives is tested against the edge being driven. The frame conflicts if its sender's hold is within the clearance of the edge, or if one of its claims is, unless that claim includes the node the robot just left (a robot behind announces the edge into that node and waits for the claim to clear). On a conflict the agent cancels the driver call, which must halt the robot, asks the driver to retreat to the node it left, and announces again, after which the rules of section 3.2 apply as usual. The driver interface gains one method, `retreat`. The option is off by default, so the protocol in sections 3.1 to 3.3 is unchanged. ## 4. Method ### 4.1 Simulator Agents run unchanged on a virtual clock (`vclock.py`), so a run takes a fraction of a second and repeats exactly for a given seed. The simulated radio is one collision domain in which every robot hears every other. A frame has 30 ms of airtime, and a frame that overlaps another on air is lost. Delivery has a random delay of 50 to 300 ms. On top of that each frame is lost with a set probability. A simulated driver moves a robot in a straight line between node coordinates at 0.5 m/s, with no dynamics, tracking error or obstacles. It can be cancelled part-way and can retreat. A seed fixes the routes (not dependent on the loss rate), the radio's random choices and each agent's own random timing. ### 4.2 Map and scenario We used one map, generated with `make_map.py`: 16 rows × 60 m, 1.2 m apart, a node every 3 m, 336 nodes, no docks. We used the `random` scenario only: a random start and goal per robot, with every robot standing at its start node from time zero. We used 2, 3 and 4 robots, frame loss of 0, 10 and 20%, and seeds 0 to 9, so 90 runs per configuration, and ran them with and without the mid-edge stop. A second sweep used 6 legs per route (each leg a shortest path to a new random node), 2 and 4 robots, 0 and 20% loss and 5 seeds, so 20 runs per configuration. A third sweep used 20 legs per route (about 20 times the run time), 2, 3 and 4 robots, 0, 10 and 20% loss and seeds 0 to 9, so 90 runs per configuration, with a timeout of 18,000 s. ### 4.3 Outcomes A run is a *close approach* if two moving robots come within the 1 m clearance. A run is *unfinished* if any robot has not reached the end of its route by the timeout (600 s of unscaled time per run, 5400 s for the 6-leg sweep). We did not classify unfinished runs into deadlock and slow progress. The package notes that a deadlocked run ends at the timeout. ## 5. Results **Table 1.** Large map, 1 leg, 10 seeds per cell. All were with 4 robots and seed 0, at each of the three loss rates. None occurred with 2 or 3 robots. The closest separation in each was 0.00 m, meaning two robots at the same point. No close approach occurred in the 20 six-leg runs, but that is a small sample. Each of the three runs had at least one lost frame (10, 17 and 23 lost frames at 0, 10 and 20% loss). At 0% random loss the only losses are frames that overlapped on air. We found no close approach in a run with no lost frames. This is an association in 90 runs, not a controlled test. Outcomes changed little between 0, 10 and 20% random loss: the 3-robot and 4-robot cells are identical, and the 2-robot cell loses one finished run. With 10 seeds per cell we cannot resolve small differences. In this sweep the routes are the same at every loss rate, so the dominant effect is route conflict and start-up overlap rather than the random loss rate. Section 5.4 shows that this changes with longer routes. ### 5.2 A traced close approach With 4 robots, seed 0 and 0% random loss, robots 1 and 2 each had a route through node 274, robot 1 arriving from node 315 and robot 2 from node 275. At about 58.4 s and 58.6 s the frames of robot 2 and robot 1, each naming node 274, were both lost to channel overlap. Neither robot knew the other existed, and both set off at 59.8 s. Robot 1 reached node 274 at 62.2 s. Its arrival frame is sent only after the 2 s wait of section 3.2 and reached robot 2 at 64.3 s. By then robot 2 was 2.3 m along its 3 m edge, 0.7 m from node 274, where robot 1 stood. Without the stop, robot 2 drove on and the two robots met at the same point. Two properties combine: the first frame is sent once and not repeated, and a robot already driving an edge cannot react to a frame that arrives mid-edge. ### 5.3 The mid-edge stop With the stop, robot 2 in the traced run cancelled its drive when the frame arrived, at 64.3 s, and retreated to node 275. The closest separation in the run rose from 0.00 m to 0.73 m. It is still under the 1 m clearance. The cause is in the timing: the arrival frame is delayed by 2 s, and at 0.5 m/s a robot covers 1.0 m in that time, the same as the clearance. A robot that has set off toward a node a peer has just reached has already used up the clearance when the frame arrives. The stop therefore reduces the worst case but cannot restore the clearance on its own. The number of close approaches was 3 of 90 with and without the stop, and the same run (seed 0, 4 robots) was the close approach in each of the three loss cells. Fewer runs finished in the 6-leg sweep (7 of 20 against 10 of 20) and in the 20-leg sweep (14 of 90 against 23 of 90), with more side-steps in the 4-robot cells (13.2 and 14.8 against 8.8 and 12.8). With 20 runs per configuration we do not claim that the stop reduces completion, but we found no benefit in it either. The stop was triggered rarely with 2 or 3 robots (0.0 to 0.2 per run) and most often with 4 robots at 0% loss in the 6-leg sweep (5.8 per run). ### 5.4 Long routes **Table 3.** Large map, 20 legs, 10 seeds per cell. In the 6-leg sweep the finishing runs took a median of about 910 to 1,910 s, and runs with 4 robots used 8.8 to 12.8 side-steps on average across all robots, against a cap of 10 per robot. ## 6. Discussion The protocol as implemented does not guarantee clearance under frame loss, even with no random loss. The cause traced here is simple: a robot that has not heard a peer assumes the way is clear, and one lost frame leaves it blind for a whole edge. We tested one change, the mid-edge stop. It improved the worst separation in the traced run but not the count of close approaches, because the arrival frame lags arrival by 2 s. On 20-leg routes it removed some close approaches and caused others, and fewer runs finished. Two changes remain untested. 1. **Do not move on silence.** A robot could hold at start-up until it has heard each expected peer's hold, or resend its start-up frame until it hears a reply. 2. **Release and expire.** A finished robot sends a final frame that frees its hold, and a peer's hold expires if the peer is silent for a set time. The second also covers a robot that fails. A third follows from section 5.3 and is also untested: send the arrival frame at once. This needs a frame that carries the old node as a second hold, which the 8-byte frame does not allow, or a separate release frame after the 2 s. The results are limited by the simulation and by the single generated map. The radio is a single collision domain with a fixed airtime and uniform delay, and random loss is a fixed rate. A real LoRa link has bursts, hidden nodes and duty-cycle limits that are not modelled. The driver has no dynamics, so its stop is instant and its retreat has no turn. The farmer-generated field map in the repository, which is much smaller, was not used. We ran one scenario of the four the sweep offers, 10 seeds per cell, and the 6-leg sweep has 5. We did not test routes ending on parking nodes, which the package recommends. The unfinished runs are not classified. A real radio trace and a field test with two robots would be the next step before the numbers can be trusted for a deployed system. ## 7. Conclusion In simulation on a generated 336-node map, a decentralised node-claim protocol over a lossy LoRa channel produced close approaches in 3 of 90 runs with one leg per route, all with 4 robots and all with at least one lost frame. With routes 20 legs long, 18 of 90 runs had one, with 3 or 4 robots, more often as loss rose, and only 23 finished. A traced example shows how two lost frames leave two robots blind to each other, and how the 2 s delay of the arrival frame limits any reaction. Stopping a robot part-way along an edge raised the closest separation in that run from 0.00 m to 0.73 m but did not remove the close approaches. The result is a baseline: the changes above can be tested against it with the same sweep. The protocol is not safe to rely on, and the package says so. ## Data availability Code, map generator, sweep tool and tests: , branch `caatinga-dev`. The protocol as published is commit 679e72e.
